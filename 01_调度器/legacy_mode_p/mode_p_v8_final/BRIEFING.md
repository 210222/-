# MODE:P 重构简报 — 供其他 LLM 了解背景

> **用途：** 将此文件交给任何大模型，使其理解 MODE:P 的现状、问题、重构目标和约束。
> **日期：** 2026-07-15
> **版本：** v1.0

---

## 一、MODE:P 是什么

MODE:P 是"导演系统"中**面向 AI 视频生成**的管道。它读取剧本，产出 AI 视频模型可执行的提示词。

- **模型底座：** 即梦 Seedance 2.0（SD2.0）— 画布模式
- **输入：** 剧本（对白+动作描述）、空间地图（房间尺寸/光源/家具）、参考图描述
- **输出：** 故事板提示词（逐镜画面描述）+ 视频提示词（逐秒画面+运镜+音轨）
- **与其他模式的区分：** MODE:A 面向人类导演（输出文学性描述），MODE:P 面向 AI 模型（输出可渲染的精确指令）

## 二、当前架构 v7.2 — 结构与问题

### 2.1 管道规模

v7.2 是经过多次迭代叠加形成的复杂系统，包含 **11 层协议**：

| 协议 | 功能 |
|------|------|
| S-1 子代理强制执行 | 每个设计/审计步骤 = 独立 Agent 调用，禁止内联 |
| S-2 并行/串行拓扑 | 数据依赖驱动的 Wave 编排 |
| S-3 复杂度自适应路由 | F1-F7 零模型判定 -> S/M/C 三级管道深度 |
| S-4 性能强制协议 | 共享文件禁止独立加载、Gate 0 前置 |
| S-4.5 TIME_SKELETON_LOCK | Scene Designer 为唯一时间轴 Owner |
| S-4.6 YAML-Only 审计 | 审计 Agent 只读 .yml，不读 .md 推理 |
| S-5 自动迭代与版本管理 | Karpathy 式改进循环 + 结构化输出强制 |
| S-7 Performance Translation | 剧本表演注释 -> 解剖学描述 |
| S-8 算法管道 | Python 确定性代码替代 Prompt Composer 的台本组装 |
| S-9 缓存前缀注入 | 不变内容注入 system prompt 前缀 |
| Data Contract | 组件间数据契约（YAML 字段定义） |

### 2.2 Agent 生态（C-Level 完整管道，约18个Agent）

```
全局前置:
  Step 0: IMAGE_AUDIT（图片资源盘点）
  Step 0.5: OBJECT_TIMELINE（物体存在链追踪）
  Step 0.6: ANCHOR_BASELINE（角色锚点基线）
  Step 0.7: CONTEXT_PACKAGE（预编译上下文包）
  Step CR.1-CR.4: F1-F7 复杂度判定

设计阶段（串行，数据依赖）:
  Shot Architect -> Movement Designer -> Composition Designer

门禁:
  Gate 0 前置扫描（R01-R17 正则）-> 阻断/警告/通过

审计阶段:
  Scene Auditor（四阶段合并: Gate 0 + 设计审计 + 时间轴同构 + 台本审计）
  或 C-Level: Scene Design Auditor + Scene Script Auditor + Scene Anchor Auditor

规划阶段（条件执行，按复杂度）:
  Storyboard Planner -> Prompt Composer

全场景后验证（C-Level专用）:
  5 位多维探究专家并行（红队对抗/边界测验/假设驱动/模式匹配/结构同构）
  -> 多方会诊 -> Render Packager -> Object Existence Verifier
  -> Render Verifier（Seko 渲染后 7 维验证）

知识蒸馏:
  STATE.md / P-STATE.md 更新 -> 蒸馏引擎 -> KB 追加
```

26 个 Agent 指令文件，总计 17,214 行，约 197K tokens。

## 三、量化问题 — 注意力浪费

### 3.1 实证数据（EP14 场景 A：7 镜、31 秒、1 室、2 人、86% 固定、4 句对白）

**总消耗约 875K tokens（不含指令层 197K）**

```
🔴 纯浪费    394,587 tokens (45.1%)
   ├── SDA 零阻断审计         143,787  <- 1,040 行输出，发现 0 个阻断
   ├── SSA 正则可替代审计      150,000  <- 3 个阻断全可用正则检出，无需 LLM
   ├── 上游输出全量读取(仅30%使用) 77,900
   ├── 空间描述跨 9 个文件重复   14,200  <- 净新增信息 = 0
   ├── 形式主义辩护             4,200  <- Movement Designer 978 行，有效密度 0.1%
   └── 假阳性阻断的 LLM 推理     4,500

🟡 低效浪费  239,064 tokens (27.3%)
   ├── KB 完整加载(720条,42K/次) 102,600  <- 实际使用约 30%
   ├── 共享文件被读 65 次         74,000  <- P-CONSTITUTION 被 13 个 Agent 各自读取
   ├── Composition 33 次工具调用  26,764
   └── 审计报告叙事包装           35,700

🟢 合理消耗  242,043 tokens (27.6%)
   ├── Prompt Composer 台本      35,371
   ├── Storyboard Planner 骨架   56,935
   ├── Shot Architect 机位       13,954
   └── 各 Agent 部分净推理        90,783
```

**仅 27.6% 的 token 产生了净设计价值。**

### 3.2 最严重浪费

| 浪费现象 | 规模 | 浪费比 |
|---------|------|-------|
| Movement Designer 论证"6 个固定镜头合理" | 978 行 / 有效信息密度 0.1% | 1 个运镜参数 : 978 行 |
| SSA 用 177K tokens 检测了 3 项正则问题 | 150K 可替代 | 5 个词的错误 -> 477K tokens |
| SDA 143.8K tokens 发现 0 个阻断 | ROI = 0.11 | — |
| 同一空间描述出现 9 次 | 累计 130-180K tokens | 净新增信息 = 0 |
| P-CONSTITUTION 被 13 个 Agent 各自 Read | 浪费 175,500 tokens | — |

### 3.3 三大根因

1. **"独立验证 = 独立加载"** — 宪法第七条要求独立上下文，被误解为每个 Agent 各自加载全部共享文件
2. **"论证替代决策"** — Agent 被要求为"什么都不做"写 700 行辩护，因为管道结构要求每个 Agent 必须产出
3. **"确定性检查嵌入概率性验证"** — Gate 0 正则（零 token，100% 准确）被放在 LLM 审计之后执行，宪法第五条被违反

## 四、重构目标

### 4.1 核心原则

> **将 MODE:P 中所有跟"设计"无关的东西砍掉。让 MODE:P 成为一个真正的导演。**

- 导演做设计，不是做合规检查
- 知识内化为直觉，不是外部检索的规则
- 质量靠专业审查（DP），不是靠多层审计
- 自然语言通信，不是 YAML/JSON 结构化

### 4.2 目标架构

```
剧本 + 空间地图 + 参考图
        │
        ▼
   ┌──────────┐     ┌──────────┐
   │  导演Agent │────>│  DP Agent │
   │  创作·设计 │<────│  审查·反馈 │
   └──────────┘     └──────────┘
        │                  │
        │   DP:"没问题"     │
        ▼                  ▼
   故事板提示词          自然语言反馈
   视频提示词             -> 导演修改
   (最终交付)
```

### 4.3 必须砍掉的（v7.2 -> 移除）

| 移除项 | 原因 |
|--------|------|
| 独立 Shot/Movement/Composition 三 Agent 串行 | 一个导演 Agent 可以同时考虑机位/运镜/构图/光影 |
| Scene Design Auditor (SDA) | 零阻断，纯浪费 |
| Scene Script Auditor (SSA) | 3 个阻断全可正则检出 |
| Scene Anchor Auditor | 单场景无需跨场景锚点 |
| 5 专家多方会诊 | S/M 级发现率趋近于零 |
| Storyboard Planner 独立 Agent | 导演直接出最终格式 |
| Prompt Composer 独立 Agent | 同上 |
| Object Existence Verifier | 物品由导演在设计中自然追踪 |
| Render Packager | Seko 平台格式不需要 |
| Render Verifier | 渲染后验证不在此管道范围 |
| YAML 强制输出 | 自然语言足够 |
| KB 规则 ID 引用 | 形式主义 |
| 所有审计报告格式 | 用 DP 自然语言反馈替代 |
| CONTEXT_PACKAGE 预编译 | KB 知识直接内化在 system prompt 中 |
| 缓存前缀注入 | 不再有多个 Agent 重复加载 |
| OBJECT_TIMELINE | 物品追踪由导演自然处理 |
| ANCHOR_BASELINE 独立步骤 | 空间/角色锚点由导演从输入中直接使用 |
| F1-F7 复杂度路由 | 所有场景走同一流程 |

### 4.4 保留的（从 v7.2 继承）

| 保留项 | 用途 |
|--------|------|
| SD2.0 渲染知识（sd2_model_capability.md） | 内化到导演和 DP 的 system prompt |
| 四大知识域（运镜/构图/光影/切换） | 从 03_导演知识库_v5.0.md 提取核心原则，内化到 system prompt |
| 画布宪法核心原则（画面可见性、正向语言、光源锚定、15秒上限） | 内化 |

### 4.5 待决策项

| 问题 | 选项 |
|------|------|
| Gate 0 正则扫描 | A) 完全移除 B) 保留为导演交付前的零 token 自动检查 |
| Agent 数量 | A) 1 个导演全包 B) 导演 + 运镜/构图/光影专项 Agent 并行 |
| 复杂度路由 | A) 完全移除 B) 保留 F1-F7 判定，简单场景跳过 DP |

## 五、技术约束

### 5.1 模型底座：即梦 SD2.0

**核心机制：所有 token 是正向指令。没有否定架构。**

- 绝对禁止：不要、禁止、避免、不能、不应、勿、别（会被当作正向指令执行）
- 绝对禁止：悲伤、愤怒、恐惧、紧张、焦虑（SD2.0 不理解情绪标签，会随机化）
- 绝对禁止：仿佛、好像、宛如、犹如、似乎、隐约（文学修饰对 SD2.0 是噪声）
- 必须用物理描述替代："指关节发白" 不是 "愤怒" / "S3速度，3秒推进约2米" 不是 "缓缓推近"

**硬上限：**
- 单段 <= 15 秒（模型时序注意力窗口衰减）
- 多人面部 <= 2 人（>=3 人 -> 面部特征融合/混淆）
- 同时核心动作 <= 1 个（多动作 -> 机器人式运动）
- 文字不可控（模型未优化文字渲染 -> 必乱码）
- 瞳孔控制不可控

**提示词结构规则：** 角色锚点在最前面 -> 空间锚点 -> 动作描述 -> 光影/风格在最后

**已知退化模式：**
- 运动优先于身份（动作生动度与面部保真度冲突时，系统性地优先运动）
- 提示词泄漏（光影描述会意外改写物体颜色）

### 5.2 不需要管的

- Seko 平台格式（【镜头参数卡】、@图片N、C1-C4 骨架、禁止块等）
- 多 Agent 间通信协议（只有 2 个 Agent）
- 知识蒸馏引擎（不在本次重构范围）

## 七、给接手 LLM 的建议

1. **先理解浪费真相** — MODE:P v7.2 的浪费比任何架构文档都重要，只看架构图看不出来问题在哪
2. **核心矛盾** — v7.2 把导演当成了合规检查员。重构的方向是让导演重新成为导演
3. **所有设计决策问自己** — 这个东西是帮导演做设计的，还是帮系统做管理的？如果是后者，砍掉
4. **SD2.0 的约束不能妥协** — 正向语言、无否定词、物理描述替代情绪词 —— 这是模型的底层事实，不是建议
5. **简洁优于完备** — 宁可少一个检查步骤，不要多一层"以防万一"
