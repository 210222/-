# MODE:P v8.0 — Loop Controller

> 编排导演(Director)与摄影指导(DP)之间的自然审查循环。
> 本文件是操作规范 —— 人类操作员或上层编排系统按此执行。

---

## 1. 系统概述

MODE:P v8.0 只有 **2 个 Agent** 和 **1 个循环**:

```
          ┌──────────────────────┐
          │    Loop Controller    │  (人 or 编排系统执行)
          └──────────┬───────────┘
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     ┌─────────┐          ┌─────────┐
     │ Director│─场景设计→│   DP    │
     │ (创作)  │←─反馈───│ (审查)  │
     └─────────┘          └─────────┘
```

- **Director**: 读剧本、空间地图、参考图 → 输出完整场景设计(故事板提示词 + 视频提示词)
- **DP**: 读场景设计 → 输出自然语言技术反馈
- **循环**: DP 说"没问题" → 交付。DP 提意见 → Director 修改 → 再送 DP 审查。

**核心原则:**
- 循环是 **自然的** —— 结束条件是 DP 确认通过,不是计数器归零
- 只有 2 个 Agent 和 2 个产出文件,没有其他中间产物
- 所有输出是 **自然语言** —— 人可读,不需要 YAML/JSON/结构化审计
- 所有约束(空间可行性、视觉连续性、SD2.0 兼容性)内化在 Agent 的 system prompt 中

---

## 2. 输入要求

启动循环前必须准备好三项输入:

| 输入 | 格式 | 内容 |
|------|------|------|
| 剧本文本 | .txt/.md | 场景的对白和动作描述 |
| 空间地图 | .md | 房间尺寸、门窗位置、家具布局、光源位置 |
| 参考图描述 | .md | 色调、构图、光影意向的文本描述 |

可选: 角色外观描述(2-3条/角色)、道具清单。

---

## 3. 执行流程

```
第1步: 读取输入(剧本 + 空间地图 + 参考图描述)

第2步: 启动 Director (draft 阶段)
       → 拿到 session_design.md (故事板 + 视频提示词)

第3步: 启动 DP (审查阶段)
       → 拿到自然语言反馈

第4步: 判断 DP 反馈
       ├─ 批准(含"没问题"等) → 跳第6步交付
       └─ 有修改意见 → 继续第5步

第5步: 检查轮次: if round >= 5 → 强制交付(附带已知问题)
       否则: 将 DP 反馈传给 Director (revise 阶段)
       → Director 更新 session_design.md → round += 1 → 回到第3步

第6步: 交付最终输出
```

**伪代码参考:**
```
round = 1; MAX = 5
session_design = launch_director("draft", script, space_map, refs)
loop:
  feedback = launch_dp(session_design)
  if is_approved(feedback): break
  if round >= MAX: deliver_with_issues(feedback); break
  session_design = launch_director("revise", script, space_map, refs,
                                    session_design, feedback)
  round += 1
deliver(session_design)
```

## 4. 启动 Director Agent

### 4.1 工作模式

| 模式 | 何时用 | 传入内容 | 产出 |
|------|--------|----------|------|
| draft | 首次设计 | 剧本 + 空间地图 + 参考图描述 | 完整场景设计 |
| revise | 反馈后修改 | 上述 + 上一版场景设计 + DP 反馈全文 | 更新后场景设计 |

> SD2.0 兼容性问题在 revise 模式中自然处理,不需要单独的模式。

### 4.2 传给 Director 的内容

**draft 模式:**
```
你看到的信息:
- 剧本: [路径/剧本.md]
- 空间地图: [路径/空间地图.md]
- 参考图描述: [路径/参考图描述.md]

请进入 draft 阶段,设计完整的场景。产出包含故事板提示词和视频提示词两部分。
格式参考 storyboard_template.md 和 video_template.md。
```

**revise 模式 —— 在 draft 内容基础上增加:**
```
- 你上一版的场景设计: [路径/session_design.md]
- DP 审查反馈:
  [粘贴反馈全文]

请进入 revise 阶段。逐条处理: 说得对→改。说得不对→保留(附理由)。
矛盾建议按直觉裁决(优先级: 空间安全 > 关系线 > 动作连续 > 构图 > 光影 > 运镜风格)。
更新整个场景设计文档。
```

### 4.3 预期产出

一个完整的 `.md` 文件,包含两个部分:
- 故事板提示词 (以 `# [场景名] · 故事板` 开头)
- 视频提示词 (以 `# [场景名] · 视频提示词` 开头)

---

## 5. 启动 DP Agent

传给 DP:
```
你看到的信息:
- 导演的场景设计: [路径/session_design.md]
- 空间地图(供参考): [路径/空间地图.md]

请审查这份场景设计。用自然语言给反馈,像片场沟通一样。
```

**预期产出** —— 自然语言文本,两种形态:

**通过形态:** "看了一遍。空间可行 · 视觉连续 · 运镜有动机 · 构图清晰 · 光影有锚点 · SD2.0 兼容。没有需要改的地方。" 或简化为 "没问题。可以交付。"

**反馈形态(含具体意见):** "镜 3 的推进轨迹会被桌子挡住——房间实际深度只有 2 米。镜 5 的主光源方向在参考图里找不到锚点。其他没问题。"

---

## 6. 判定: DP 是否批准

### 6.1 规则

**判定为"通过"** 的条件: DP 回复中包含"没问题"、"可以交付"、"没有需要改"等明确批准信号,且没有附带任何指向具体镜头的修改要求。

**判定为"需要修订"** 的条件: 反馈中包含任何指向具体问题的表述(含"不行/问题/改/不可行/穿墙/越界/反了/不一致/没锚点/不符合/矛盾/不对/错误"等词),即使以"其他没问题"结尾。

### 6.2 实现参考

人类操作员: 直接阅读,凭常识判定。

编排系统: 关键词检测。
```
def is_approved(text):
    revision_kws = ["不行","问题","改","不可行","穿墙","越界",
                    "反了","不一致","没锚点","不符合","矛盾","不对","错误"]
    approval_kws = ["没问题","可以交付","没有需要改"]
    has_revision = any(kw in text for kw in revision_kws)
    has_approval = any(kw in text for kw in approval_kws)
    if has_approval and not has_revision: return True
    return False  # 有修订要求或无法判定 → 送回修订
```

> 关键词检测是辅助手段。无法判定的情况(如无关键词命中),人工介入判断。循环超过 3 轮也应人工检查是否存在沟通卡顿。

---

## 7. 轮次跟踪与安全网

### 7.1 计数器

`round` 从 1 开始,每次 Director 完成产出后、送 DP 前递增。

- Round 1: Director draft → DP 审查
- Round 2: Director revise → DP 审查
- Round 3-4: 同上
- Round 5: 最后一轮。DP 仍未批准则强制交付。

### 7.2 达到上限的处理

```
if round >= 5 and not approved:
    known_issues = latest_feedback
    # 在交付文件开头添加:
    # "注意: 本场景设计经过 5 轮审查后交付。以下问题未完全解决:"
    # [列出 DP 最后一轮反馈中的问题]
    deliver(session_design, known_issues)
```

### 7.3 边缘情况

| 场景 | 处理 |
|------|------|
| DP 反馈为空 | 重试一次。仍为空 → 视为批准,交付 |
| Director 输出为空 | 重试一次。仍为空 → 报错终止 |
| 同一问题重复 3 轮 | 视为"已知争议",强制交付时注明"Director 保留意见" |
| 人工中途介入 | 可随时 override 循环(提前交付或退回修改) |

## 8. 最终交付

### 8.1 标准交付

```
delivery/
├── 故事板提示词.md     # 从 session_design.md 提取
└── 视频提示词.md       # 从 session_design.md 提取
```

或单个文件 `delivery/场景设计_最终版.md`。

**无额外文件:** 不需要审计报告、YAML 输出、合规清单、Gate 0 报告、轮次统计。

### 8.2 带已知问题的交付(第 5 轮强制)

在文件开头增加:
```
> 注意: 本设计经过 5 轮审查交付,以下问题未完全解决:
> - [问题 1]
> - [问题 2]
> 上述问题不影响主要视觉方案完整性,可在实际拍摄中酌情处理。
```

### 8.3 交付后

Loop Controller 工作结束。产出交付下游(Storyboard Artist 或 SD2.0 生成)。不触发后续自动化审计。

## 9. 人类操作员速查

**一轮循环的典型操作:**
```
1. 读输入文件 ✓
2. 启动 Director (draft) → 保存为 session_design.md
3. 启动 DP (审查) → 读输出
4. "没问题"? → 交付。有意见? → 继续
5. 将 DP 意见传给 Director (revise) → 更新 session_design.md → 回到第 3 步
6. 复制到交付目录
```

**建议文件布局:**
```
input/script.md  input/space_map.md  input/references.md
work/session_design.md
delivery/故事板提示词.md  delivery/视频提示词.md
```

**何时人工介入:**
- 同一意见重复 3 轮 → 判断争议点
- 第 5 轮未通过 → 判断是否继续
- DP 输出无法判定(无关键词) → 人工阅读
- Agent 调用异常 → 检查

## 10. 与 v7.2 的关键差异

| v7.2 (旧) | v8.0 (新) |
|-----------|-----------|
| ~18 个 Agent 串行调用 | 2 个 Agent 在循环中协作 |
| 11 层协议栈(YAML/审计/合规) | 0 层协议 —— 自然语言传递 |
| F1-F7 复杂度路由 | 无路由 —— 一个循环走到底 |
| Gate 0 正则扫描预检 | 无预检 —— 约束内化在 Agent 中 |
| block_count + 收敛算法判定 | DP 说"没问题"即结束 |
| ~875K tokens / 7 镜 | ~50-100K tokens(预计) |
| YAML 输出供下游消费 | 自然语言输出给人读 |
