# MODE:P 场景复杂度自适应路由系统 v1.0

> **定位:** MODE:P管道前置路由层——根据场景复杂度自动选择执行深度，消除简单场景的过度工程化。
> **触发时机:** MODE:P启动时·调度器自执行·零模型判断·在§-2拓扑分析之后·Agent调用之前。
> **设计依据:** EP14场景A红队审计发现——7镜·31秒·1室2人·86%固定·4句对白→10次Agent调用·~8,200行·~232K tokens·3-4倍过度工程化。Movement Designer产出978行论证"6个固定镜头是合理的"→橡皮图章。
> **宪法约束:** 画布宪法第五条——确定性优先于概率性。复杂度分类100%调度器自执行·零模型判断。
> **版本:** v1.0 · 建立日期: 2026-07-07
> **关联文件:** dispatcher_v5.0.md §-3(插入文本) · dispatcher_§-3_insert.txt(可直接复制粘贴)

# §1 问题陈述

## 1.1 根因

当前MODE:P管道对所有场景运行相同的完整流程：三Agent串行设计→Scene Design Auditor→Storyboard Planner→Prompt Composer→Scene Script Auditor→Storyboard生成审计→全场景后6专家多方会诊。无论场景是7镜室内对话还是30镜动作大片，都跑完全部~18次Agent调用。

**核心缺陷:** 管道深度与场景复杂度不匹配。简单静态场景被当作复杂动作场景处理。

## 1.2 EP14场景A量化证据

| 指标 | 实际消耗 | 合理预期 | 过度倍数 |
|------|:------:|:------:|:------:|
| Agent调用次数 | 10次 | ~3次 | 3.3x |
| 输出总行数 | ~8,200行 | ~1,200行 | 6.8x |
| Token消耗 | ~232K | ~50K | 4.6x |
| Movement Designer | 978行论证"6个固定镜头合理" | 0行 | inf |

## 1.3 冗余来源解剖

| 冗余项 | 当前行数 | 根因 | 本路由后 |
|--------|:------:|------|:------:|
| Movement Designer独立Agent | ~978 | 6/7镜固定·运镜设计全冗余 | 合并→≤50行 |
| 运镜合理性论证 | ~700 | "镜#3固定·因为角色静止..." | 禁止·R-SFAST-02 |
| 独立Composition Designer | ~1,500 | 单室·光源从空间地图直取 | 合并入Scene Designer |
| 独立Prompt Composer | ~1,200 | 简单对白·无复杂时序 | 合并入Scene Designer |
| 独立Storyboard Planner | ~800 | 仅4句对白·TIME_SKELETON trivial | 跳过 |
| 独立SDA+SSA审计 | ~1,200 | 两审计可合并 | 合并入Scene Auditor |
| 5专家多方会诊 | ~2,500 | 简单场景无多维验证需求 | 跳过 |
| **总计** | **~8,878** | | **→ ~1,200** |

# §2 三级复杂度分类

## 2.1 分类原则

1. **确定性:** 所有字段从输入文件可计数·零模型判断·调度器自执行
2. **保守降级:** 任何字段不确定时·降级到更高复杂度
3. **场景级独立:** 每场景独立分类·不跨场景累积复杂度
4. **用户可覆盖:** 预执行声明后·Agent调用前·用户可手动升(不可降)等级

```
┌──────────────────────────────────────────────────────────────────────┐
│              场景复杂度分类 · 确定性判定矩阵                            │
│                                                                      │
│  ┌─────────┬──────────────────┬──────────────────┬──────────────────┐│
│  │ 字段    │ 🟢 S-Level       │ 🟡 M-Level       │ 🔴 C-Level       ││
│  │         │ (Simple)         │ (Moderate)       │ (Complex)        ││
│  ├─────────┼──────────────────┼──────────────────┼──────────────────┤│

│  ├─────────┼──────────────────┼──────────────────┼──────────────────┤│
│  │ F2 角色 │ ≤3个说话角色      │ ≤3个              │ ≥4个说话角色     ││
│  ├─────────┼──────────────────┼──────────────────┼──────────────────┤│
│  │ F3 对白 │ ≤5句             │ 6-15句            │ >15句            ││
│  ├─────────┼──────────────────┼──────────────────┼──────────────────┤│
│  │ F4 静态 │ ≥80%固定          │ 40%-79%           │ <40%或任意       ││
│  ├─────────┼──────────────────┼──────────────────┼──────────────────┤│
│  │ F5 运镜 │ =false           │ =true             │ =true            ││
│  ├─────────┼──────────────────┼──────────────────┼──────────────────┤│
│  │ F6 动作 │ =false           │ =true或false      │ =true·复杂动作   ││
│  └─────────┴──────────────────┴──────────────────┴──────────────────┘│
│                                                                      │
│  判定逻辑 (调度器顺序执行·首个匹配即停止):                              │
│                                                                      │
│    IF (F1==1 AND F2<=3 AND F3<=5 AND F4>=0.80                        │
│        AND F5==false AND F6==false)                                  │
│       → 🟢 S-Level                                                   │
│                                                                      │
│    ELSE IF (F2>=4 OR F3>15 OR F1>=4 OR F6==true)                     │
│       → 🔴 C-Level                                                   │
│                                                                      │
│    ELSE                                                              │
│       → 🟡 M-Level                                                   │
│                                                                      │
│  🆕 v1.1 (2026-07-07): F6==true 单独即可触发 C-Level。                │

│                                                                      │
│  不确定降级:                                                          │
│    · F4无法精确统计 → 按F5=true处理(保守)                             │
│    · F6无法判定     → 按F6=true处理(保守)                             │
│    · F7边界(4 vs 5) → 按>3处理·执行O_TIMELINE(保守)                  │
│    · 任一字段完全无法提取 → 降级C-Level·标注"字段缺失"                 │
│                                                                      │
│  用户覆盖:                                                            │
│    ✅ S→M  ✅ S→C  ✅ M→C  (保守·增加管道深度)                       │
│    ❌ M→S  ❌ C→M  ❌ C→S  (禁止·不允许减少验证深度)                  │
└──────────────────────────────────────────────────────────────────────┘
```

# §3 S-Level 管道规范 (Simple)

## 3.1 适用范围

单室内空间·≤3个说话角色·≤5句对白·≥80%静态镜头·无动作戏。
典型: 室内对话·单人独白·双人对手戏·静态氛围镜头·角色出场介绍。

## 3.2 管道拓扑

```
═══════════ 全局前置 (所有级别共享·不变) ═══════════

[Orchestrator] Step 0: IMAGE_AUDIT → 完整执行 → IMAGE_AUDIT.md + 场景列表

[Orchestrator] Step 0.5: OBJECT_TIMELINE (条件执行)
  → F7≤3: ⚡跳过·标注"F7≤3·跳过"
  → F7>3: 完整执行Step 0.5
  → 判定依据: §5

[Orchestrator] Step 0.6: ANCHOR_BASELINE (精简执行)
  → 保留: Character Anchor + Style Spine
  → 跳过: 多场景连续性校验(单场景不适用)
  → 输出: ANCHOR_BASELINE.md

═══════════ S-Level 核心管道 (2 Agent·2 Waves) ═══════════

Wave 1 (串行·1步):
  S1: [Agent] Scene Designer (三合一合并·独立Agent调用)
      ├─ 合并: Shot Architect + Movement Designer(精简) + Composition Designer
      ├─ 输入: 原始剧本 + 空间地图(ANCHOR_BASELINE §C) + 参考图 + ANCHOR_BASELINE + P-STATE
      │        + kb_index_v2.0 + P-CONSTITUTION + canvas_runtime
      ├─ 职责:
      │   1. 机位设计: 单室≤3个可用机位·景别+角度+焦段
      │   2. 运镜设计: 默认全部固定·仅标注有运镜的例外镜(R-SFAST-01~03)
      │   3. 构图光影: 从空间地图直接引用·仅补充未覆盖项(R-SFAST-04)
      │   4. 导演台本: 直接输出【镜头参数卡】+【生成指令】+【禁止】+【段末转场】
      │      (R-SFAST-05: ≤5句对白→直接嵌入音轨·不通过PLAN中转)
      ├─ 输出: 合并设计报告(含§6 YAML + 导演台本·单文件)
      └─ 硬约束:
          · 总输出 ≤ 1,500行
          · 运镜节 ≤ 50行
          · 不重复空间地图已有信息
          · 不写【设计依据】块

Wave 2 (串行·1步):
  S2: [Agent] Scene Auditor (合并审计·独立Agent调用)
      ├─ 合并: Gate 0 Scanner + Scene Design Auditor + Scene Script Auditor
      ├─ 输入: S1合并设计报告 + 空间地图 + 参考图 + ANCHOR_BASELINE + P-CONSTITUTION
      ├─ Phase 1 — Gate 0确定性扫描 (R01-R13·100%准确率)
      │   🛑任一→返回S1修复·上限1轮
      │   ✅全部→进入Phase 2
      ├─ Phase 2 — 设计审计(5维):
      │   维度A: 机位覆盖+空间可行性
      │   维度B: 运镜合理性 (R-SFAST-02橡皮图章检测·R-SFAST-03长度检测)
      │   维度C: 构图+光影·光源锚定
      │   维度D: 台本铁律合规(画布宪法第一~四条)
      │   维度E: TIME_SKELETON隐式验证(从台本反推·与对白时序对齐)
      ├─ Phase 3 — 综合裁决: 🛑→返回S1·上限2轮 / ⚠️→标注 / ✅→交付
      └─ R-AGENT-02: 只读S1输出文件·不读推理
      └─ R-AGENT-03: 审计Agent ≠ 设计Agent·独立agentId

总Agent调用: 2次 · Wall-Clock: 2 waves · 节省~89% vs C-Level
```

## 3.3 S-Level 静态快速通道规则

```

│          S-Level 静态快速通道 · 运镜设计零冗余·六条硬规则              │

│    单室场景→空间连续性自动满足·光源不变·背景统一。                     │
```

# §4 M-Level 管道规范 (Moderate)

## 4.1 适用范围

中度复杂场景: 多空间(2-3室)·动态运镜·6-15句对白·或有动作戏但角色少(≤3人)。
典型: 双空间对话·室内打斗(1-2人)·三人对话(>5句)·带横移/摇摄的场景漫游。

## 4.2 管道拓扑

```
═══════════ 全局前置 ═══════════

[O] Step 0: IMAGE_AUDIT → 完整
[O] Step 0.5: OBJECT_TIMELINE → F7>3执行·否则⚡跳过
[O] Step 0.6: ANCHOR_BASELINE → 完整(含多场景连续性)

═══════════ M-Level 核心管道 (4-7 Agent·3-4 Waves) ═══════════

── 分支判定 (基于F6) ──

路径M-A (F6=false·无动作戏):

  Wave 1 (串行·2步):
    S1: [Agent] Scene Designer (二合一: Shot Architect + Composition Designer)
        → 输出: 机位+构图合并报告 + §6 segments_camera + global_anchors
    S2: [Agent] Movement Designer (独立·读S1 §6 YAML)
        → 输出: 运镜报告 + §6 segments_movement

  Wave 2 (并行·1-2步):
    P1: [Agent] Scene Design Auditor
    P2: [Agent] Storyboard Planner (条件: F3>10 OR F1>1)

  Wave 3 (串行):
    S3: [Agent] Prompt Composer (独立)
        → 有PLAN: 读PLAN §B TIME_SKELETON → 派生逐秒画面
        → 无PLAN: 从设计报告直接生成台本·TIME_SKELETON内嵌

  Wave 4 (并行·1-2步):
    P3: [Agent] Scene Script Auditor
    P4: [Agent] Scene Anchor Auditor P2 (条件: 场景数≥2)

路径M-B (F6=true·有动作戏):
  Wave 1 (3步): Shot Architect → Movement Designer → Composition Designer
  后续同M-A Wave 2-4

跳过项 (vs C-Level):
  ✗ 5专家并行 + 多方会诊
  ✗ Storyboard Generator + Auditor
  ✗ Render Verifier + Deep Repair Loop

Agent调用: 4-7次 · Waves: 3-4 · 节省~61-72%
```

# §8 与 §-1(子代理) §-2(拓扑) 兼容性

## 8.1 §-1 子代理协议兼容性

| §-1 约束 | §-3 实现 | 状态 |

| R-AGENT-02 审计只读输出 | 审计Agent只读设计输出文件·不读推理·合并角色不改变隔离 | 兼容 |

## 8.2 §-2 并行拓扑兼容性

§-3是§-2的精简实现·非替代·非违反。
- C-Level管道 = §-2原文·拓扑完全一致
- S/M-Level管道 = §-2的精简子集·并行/串行逻辑一致
- 数据依赖关系不变(机位→运镜·设计→审计)
- 合并Agent内部按域顺序执行·不是"并行合并"·是"串行合并"
