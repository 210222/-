# 架构与施工方案权威判定记录 001

## 结论

本轮以架构为规范真源，以施工方案为派生执行层。由于架构 v2.0 对施工治理存在
可证实的缺口，处理顺序是“失败关闭 A0 → 发布 v2.1 架构修订 → 重生成施工方案
→ 重新领取并验证 A0”，而不是任选架构或旧施工方案继续施工。

## 判定依据

| 层级 | 作用 | 本轮处理 |
|---|---|---|
| 用户目标与生产安全 | 定义最终目标和不可越过的外部边界 | 最高优先级；v4 与生产入口不动 |
| 架构权威包 | 定义系统不变量、阶段和职责 | v2.0 保留；用 v2.1 修订缺口 |
| 机器施工任务表 | 将架构拆成可领取、可验证工作包 | 必须适配 v2.1 |
| 施工协议和命令 | 约束实际施工行为 | 必须适配任务表 |
| 旧 R/DDO/CPL 和实现 | 证据、兼容输入与反例 | 历史只读，不再选任务 |

## 已考虑的替代方案

### 方案 A：完全以旧施工方案为准

拒绝。旧队列并列拥有权威，且继续围绕旧 B1 边界修补，无法实现架构 v2 的唯一
Artifact、确定性组装和单一 ReleaseLedger。

### 方案 B：完全以架构 v2.0 原文为准，不做修订

拒绝。v2.0 给出了正确方向，但没有明确独占写入所有权、阶段状态映射和 A10 两个人工
门的机器语义。直接施工会让同一文件被多个任务绑定、A7 阶段错误、A10 自报批准。

### 方案 C：只在控制器中增加特例

拒绝。代码特例会变成未被架构授权的隐性设计，后续任务表仍可再次偏离。

### 方案 D：版本化修订架构，再重生成施工层

采用。它保留 v2.0 原始哈希与设计来源，同时让新增约束可审计、可锁定、可回归。

## 变更边界

- 不修改导演双循环和媒体闭环的核心产品架构；
- 不恢复 27K 总提示词；
- 不调用创作模型或真实媒体服务；
- 不修改 v4 生产入口；
- 不把本轮治理修复误报为 A1–A10 的业务实现完成。
