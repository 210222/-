# R3.2 terminal-state and local-environment change request

Status: `PENDING_OWNER_AUTHORIZATION`  
This request does not alter the frozen v1.1 plan, controller, v4 source, or `.claude/settings.local.json`.

## Confirmed contract conflict

The current controller emits `V_TASK_REVALIDATION_REQUIRED` after its repair queue. R3.2 instead requires `local_ready_machine_generated`. Neither state is implemented as a machine-generated artifact that can truthfully mean a Director runtime is ready. Renaming a report or manually editing controller state is prohibited.

The construction plan must preserve this distinction:

- `BASELINE_REPAIR_AUDITED`: old vNext repair evidence, tests, and task reconciliation have passed. It does **not** start the Director runtime, Shadow, production, or media acceptance.
- `DIRECTOR_SHADOW_READY`: only becomes possible after the separate DDO chain, Holdout, visual-media checks, and an owner approval.
- `PRODUCTION_READY`: remains an explicit owner decision after real visual acceptance; it can never be inferred from a text/unit-test state.

## Proposed controlled rebase

Create a new controller generation rather than modifying historical R0-R3 evidence in place.

1. Define `BASELINE_REPAIR_AUDITED` as the machine terminal state after a fresh V10.6 audit and all baseline required checks.
2. Replace the ambiguous R3.2 readiness requirement with a named baseline-audit artifact whose schema includes the 70-task materialized ledger, vNext test results, v4 source/package boundary evidence, and explicit non-production flags.
3. Create the DDO work queue only after this baseline state. DDO has its own `DIRECTOR_SHADOW_READY` and `PRODUCTION_READY` gates; it must not reuse R3.2 labels.
4. Invalidate/revalidate only the controller/task-registry evidence affected by this new generation. Preserve R0-R3 historical artifacts as immutable records.

## Local settings / v4 package boundary

`mode_p/test_active_entrypoints.py` currently asserts that `.claude/settings.local.json` is absent from the live working tree, while `.gitignore` explicitly marks that file machine-local. Those are two different conditions: packaging safety versus local-workspace hygiene.

The proposed test arrangement preserves the user's local file and avoids silently weakening package safety:

1. Leave the live file in place, hash it before and after every test, and never copy it into a test artifact.
2. Build a hermetic staging tree from the package allowlist/tracked project inputs, excluding ignored machine-local paths.
3. Run the v4 entrypoint/package-boundary suite in that staging tree, proving the package contains no local permissions file.
4. Record the live-workspace assertion separately as `LOCAL_PERMISSION_FILE_PRESERVED`, not as a source regression failure.
5. Do not modify `mode_p/test_active_entrypoints.py` or delete/move `settings.local.json` without a separate owner decision.
