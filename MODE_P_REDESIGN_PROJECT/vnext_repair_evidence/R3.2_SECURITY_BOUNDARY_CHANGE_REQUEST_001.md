# R3.2 security-boundary construction change request

Status: `PENDING_OWNER_AUTHORIZATION`  
Does not activate the Director runtime, Shadow, production, external generation, or media acceptance.

## Why this needs a separate authorization

The existing R3.2 controller task is an audit task. Its allowed paths include evidence and `mode_p_vnext/tests/**`, but exclude the source modules that own the security boundary. During the R3.2 audit, the following real gap was verified:

- `knowledge_security.py` quarantines untrusted knowledge-card evidence, but no shared enforcement is applied when a `ScriptFact`, `AssetBinding` metadata field, or `ExternalFeedback` object is constructed.
- `test_v9_5_security.py` proves only a small subset of authorization/path behavior; it does not prove prompt-injection quarantine or no-raw-text leakage for all four input families.
- `external_feedback.py` is a data class with no source/project validation, no safe runtime metadata projection, and no hard rejection of a caller-provided auto-modification request.

Changing those source modules inside R3.2 would violate the current controller contract. The source edits were therefore reverted before the task is released.

## Proposed controlled scope

Create a new, explicitly authorized security-remediation task. Do not silently expand R3.2 and do not rewrite R0-R3 historical evidence.

Allowed source paths:

- `01_调度器/mode_p_vnext/knowledge_security.py`
- `01_调度器/mode_p_vnext/schema/fact_registry.py`
- `01_调度器/mode_p_vnext/schema/asset_binding.py`
- `01_调度器/mode_p_vnext/external_feedback.py`

Allowed verification/evidence paths:

- `01_调度器/mode_p_vnext/tests/test_v3_7_prompt_injection.py`
- `01_调度器/mode_p_vnext/tests/test_v9_5_security.py`
- `01_调度器/mode_p_vnext/tests/test_v3_5_retrieval_budget.py`
- `MODE_P_REDESIGN_PROJECT/vnext_repair_evidence/**`

## Required behavior

1. Raw knowledge, screenplay/fact input, asset metadata, and external feedback remain data, never instructions.
2. Instruction-like payloads are quarantined or rejected before they enter a Director/retrieval/prompt/runtime packet. Error and audit records must contain only safe identifiers, hashes, and reason codes, never raw payload text.
3. Clean text remains tagged as untrusted data. Runtime-facing metadata omits raw external-feedback content and asset notes.
4. Assets and external feedback must be explicitly project-scoped at the point where they are admitted to a runtime operation; an absent or mismatched project scope fails closed.
5. External feedback cannot auto-modify knowledge. It may create a review record only.
6. No v4 source, `.claude/settings.local.json`, production entry, external model call, or media asset may be changed or invoked.

## Required verification

- Dedicated V3.7 tests cover English, Chinese, normalized/full-width, and zero-width instruction attempts.
- Tests cover knowledge-card retrieval, script/fact source, asset metadata, and external feedback separately.
- Tests prove raw payload absence from exceptions, events, snapshots, and runtime metadata.
- V9.5 tests cover unauthorized assets, path escape, active cross-project rejection, project-scope omission, feedback auto-modification rejection, and metadata leakage.
- Run the affected dependency closure and the full `mode_p_vnext/tests` suite with no skipped new security tests.
- Record a new evidence overlay; it may advance V3.7/V9.5 only when their dependency closures and source hashes are current. It must not claim V10.6, `LOCAL_VNEXT_READY`, production readiness, or visual media acceptance.

## Authorization requested before implementation

Authorize a controlled acceptance-contract rebase that adds this new task and these allowed source paths, while keeping `.claude/settings.local.json` untouched and v4 source immutable.
