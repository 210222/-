## 1. 执行摘要

四个修复方案理论上可独立节省约 **530K--1,005K tokens**。扣除重叠后，联合实施现实预期节省 **~470K tokens/场景** (53.7% reduction)，将旧管道的 875K 压缩至约 **405K tokens/场景**。

## 2. 逐修复独立计算

### 修复A: Context Package (预编译场景上下文包)

**规范来源:** context_package_spec_v1.0.md

**机制:** 调度器在Agent启动前一次性生成 CONTEXT_PACKAGE (8K)，替代每个Agent各自Read 5个共享文件(P-CONSTITUTION~15K·P-STATE~5K·canvas_runtime~5K·ANCHOR_BASELINE~4K·IMAGE_AUDIT~3K = 合计~32K非KB共享上下文)。调度器生成为纯文本合并·零LLM成本。

**计算方法:**

```
旧管道 (每Agent):
  P-CONSTITUTION.md     ~15K
  P-STATE.md            ~5K
  canvas_runtime.md     ~5K
  ANCHOR_BASELINE       ~4K
  IMAGE_AUDIT           ~3K
  ─────────────────────────
  合计                   ~32K/Agent (非KB共享上下文)

  加载这些文件的Agent数: 7 (Shot Architect·Movement Designer·Composition Designer·
                          SDA·Storyboard Planner·Prompt Composer·SSA)
  旧总计: 7 × 32K = ~224K

新管道:
  调度器生成 CONTEXT_PACKAGE: 0 tokens (纯文本合并·非LLM)
  每Agent Read CONTEXT_PACKAGE: ~8K
  新总计: 7 × 8K = ~56K

节省: 224K - 56K = ~168K
```

**假设:**
1. 7个Agent均全量加载5个共享文件 (保守: 部分Agent仅加载子集)
2. CONTEXT_PACKAGE生成质量达到8K目标 (需去重·精简·索引)
3. 包内信息密度足够Agent完成决策 (否则触发深读·增加成本)
4. agent_quick_ref(15K)不计入Fix A范围 (归属Fix B)

**验证:**
- 浪费报告§1(鱼骨图)确认: 7个Agent各自Read P-CONSTITUTION·P-STATE·canvas_runtime → ~21K纯重复 + 5个Agent读参考图/空间地图 → ~25-50K重复
- context_package_spec §2.2自报: "节省~27K tokens/Agent (54%减少)" → 我的32K估算与其27K接近(差异来自是否计入space_map)
- architecture_analysis §3.2核算: 场景上下文包节省~44K/Agent → 此为含KB的综合数(44K = 32K shared + 12K KB)，与我的32K(YAML不包括KB)一致

**三档估算:**
| 档位 | 受影响Agent | 每Agent节省 | 总节省 | 依据 |
|:---:|:---:|:---:|:---:|------|
| 保守 | 5 | 25K | **125K** | SDA·SSA仅加载部分共享文件·轻加载Agent不计 |
| 现实 | 7 | 28K | **196K** | 约28K = (32K包前 - 8K包后)含少量验证差异 |
| 乐观 | 10 | 30K | **300K** | 含轻加载Agent也能受益·包体积可压至5K |

**独立验证裁断: ~196K (现实)**

### 修复B: KB Quick Ref (Agent快速参考卡)

**规范来源:** agent_quick_ref_v1.0.md

**机制:** 将5个KB相关文件(P-CONSTITUTION·P-STATE·canvas_runtime·kb_index·03_导演知识库_v5.0.md的~720条规则·合计~90K)压缩为单一15K快速参考卡。每条规则缩减为"规则ID+一句话+深读路径"格式。Agent仅在需要完整条文时按需深读。

**计算方法:**

```
旧管道 (KB-using agents):
  每个KB重度Agent加载:
    03_导演知识库_v5.0.md    ~60K (720条规则全文)
    kb_index_v2.0.md         ~5K  (路由索引)
    P-CONSTITUTION.md        ~15K (宪法·与Fix A重叠)
    P-STATE.md               ~5K  (与Fix A重叠)
    canvas_runtime.md        ~5K  (与Fix A重叠)
    ─────────────────────────────────
    KB相关合计               ~90K/Agent
    其中纯KB浪费(路由后仍加载全文): ~45K (60K加载 - 15K实际需要)

  KB重度Agent数: ~5 (Scene Designer·SDA·SSA·Storyboard Planner·Composition Designer)
  KB轻度Agent数: ~2 (Prompt Composer·P-Verifier, 加载~20-30K KB内容)
  旧KB总计: 5×90K + 2×25K = 450K + 50K = ~500K

新管道:
  所有Agent Read agent_quick_ref: 15K/Agent
  7 Agent × 15K = ~105K
  按需深读成本(1-2次/场景·Read具体规则章节): ~25K
  新总计: 105K + 25K = ~130K

节省: 500K - 130K = ~370K (但含Fix A共享上下文部分)
```

**与Fix A的边界划分:**
Fix B的核心贡献是KB规则压缩(60K→15K摘要部分)，而非共享文件去重(那是Fix A的领域)。Fix B独立贡献:

```
纯KB优化部分:
  旧: 5重度Agent × 60K(KB) + 2轻度Agent × 20K(KB) = 300K + 40K = 340K (KB加载)
  新: 7 Agent × 10K (quick_ref中KB相关部分·约2/3) = 70K
  深读: ~25K
  节省: 340K - 70K - 25K = ~245K
```

**假设:**
1. 重度Agent需要60K KB中的10-15K内容 (浪费报告确认: "720条规则·实际使用~113条")
2. 按需深读触发率低 (1-2次/场景·仅碰陌生或冲突规则)
3. Quick ref质量足够: Agent在85%+情况下无需深读 (剩余15%触发深读)
4. KB摘要覆盖路由命中的全部章节 (无遗漏导致返工)

**验证:**
- 浪费报告§4浪费#4: "KB完整文件加载~150-300K tokens·实际需要~60K" → 与我的245K估算一致
- agent_quick_ref页脚自报: "7 Agent × 75K = ~525K tokens节省" → 此为含共享文件的综合数·我的纯KB贡献245K合理
- architecture_analysis §3.3: "KB快速参考卡节省~9K/Agent" → 此为仅规则压缩·不含kb_index·P-CONSTITUTION等的节省·9K×7=63K (太保守·因为未计kb_index和宪法压缩)·我的估算在63K和525K之间取中位数

**三档估算:**
| 档位 | 重度KB Agent | 每重Agent节省 | 总节省 | 依据 |
|:---:|:---:|:---:|:---:|------|
| 保守 | 4 | 40K | **160K** | 深读触发频繁(3-4次/场景)·部分Agent加载降级 |
| 现实 | 5 | 45K | **230K** | 1-2次深读·KB重度Agent准确覆盖 |
| 乐观 | 6 | 50K | **300K** | 零深读·所有Agent受益·Quick ref完全替代KB |

**独立验证裁断: ~230K (现实)**

### 修复C: Gate 0 Context-Aware (上下文感知正则扫描)

**规范来源:** gate0_context_aware_v1.0.md

**机制:** 将Gate 0确定性检查(R01-R15)从Scene Script Auditor的LLM Phase 0中移出·改为调度器自执行纯正则扫描。同时升级为区块感知扫描·消除R10在HEADER元数据("Seedance 2.0")的假阳性。

**计算方法:**

```
受影响Agent:
  1. SSA (Scene Script Auditor) — 主要受益者
     旧: ~177K total (含Phase 0 Gate扫描 + Phase 3台本审计)
     其中Gate 0 Phase 0部分: 估~30-50K (正则扫描·但在LLM上下文中执行)
     
  2. Scene Auditor Phase 0 — 次要受益者
     旧: Phase 0 ~3-5K (含Agent调用开销)
     
  3. 假阳性消除 — 间接节省
     R10在HEADER中触发"Seedance 2.0"假阳性 → 导致不必要的阻断和返工
     返工回环: ~10-20K (prompt_composer修复·重新验证)

直接节省:
  SSA Gate 0 Phase 0: ~40K (LLM token·可正则替代)
  Scene Auditor Phase 0: ~3K (Agent调用开销)  
  假阳性返工消除: ~15K
  ─────────────────────
  合计: ~58K

次级效应 (Gate 0前置后再无LLM做正则可做事):
  SSA剩余177K中·部分Gate 0检查渗入Phase 3: ~20K
  浪费报告确认: SSA的3项阻断(B01/B02/R14)全部正则可检测
  → Gate 0前置后·这3项阻断在SSA启动前已被发现和修复
  → SSA的Phase 3不需要重复检查 → 额外节省 ~20K

总计: ~78K
```

**假设:**
1. SSA的177K中·Gate 0 Phase 0及关联检查占~30-40% (~53-71K)
2. 假阳性返工每次消耗约10-20K·平均每2-3个场景触发1次
3. Gate 0升级v1.1后假阳性率从5-10%降至~0%
4. 正则扫描准确率100% (宪法第五条确认·无质疑空间)
5. SSA仍保留Phase 3深度台本审计 (不会被完全替代)

**验证:**
- 浪费报告§4浪费#3: "SSA用177K tokens LLM调用检测了3项正则可检测的阻断" → 确认SSA存在浪费·但并未说全部177K可消除
- 浪费报告§1鱼骨图: "如果先跑Gate 0正则扫描·SSA的177K token LLM调用完全不需要" → 此为极端主张·假设3项阻断在Gate 0中捕获后SSA完全不需要运行
- architecture_analysis §5.3: "Gate 0前置 → SSA从333s→估~100s (节省70%)" → 时间节省70%·并非token节省70%·但方向一致
- gate0 spec §5差异表: "v1.1假阳性率~5-10% → ~0%" → 假阳性消除确认·量级合理

**关键审慎判断:**
浪费报告称"177K完全不需要"过于乐观。因为:
1. SSA除Gate 0外·还做台本域深度宪法检查(Phase 3·画面可见性·P-FAL规避·空间锚定)
2. 即使Gate 0捕获了简单的正则违规·SSA仍需验证修复后的台本质量
3. SSA的177K包含大量文件读取(上游Agent输出)·这些读取在YAML-only修复中解决·不应计入本修复

因此, Fix C的真实贡献是消除LLM中的确定性检查部分·约**78K**(含次级效应)。

**三档估算:**
| 档位 | Gate 0 LLM成本 | 假阳性返工 | 总节省 | 依据 |
|:---:|:---:|:---:|:---:|------|
| 保守 | 30K | 5K | **35K** | Gate 0仅占SSA一小部分·假阳性极少触发 |
| 现实 | 60K | 15K | **78K** | Gate 0 Phase 0 + Phase 3重叠 + 假阳性 |
| 乐观 | 120K | 25K | **145K** | SSA大部分处理可被正则替代 |

**独立验证裁断: ~78K (现实)**

### 修复D: YAML-only Agent间通信协议

**规范来源:** yaml_only_protocol_v1.0.md

**机制:** 设计Agent产出双文件(.md供人类 + .yml供机器), 审计Agent只读.yml结构化数据, 不读推理过程·自检清单·设计依据等自由文本。

**计算方法:**

```
受影响消费者Agent (及其当前从设计报告读取的自由文本):
  
  1. Scene Auditor (旧: 设计报告完整MD ~112K)
     读取: Shot Architect.md(857行·~20K) + Movement.md(978行·~22K) + Comp.md(1631行·~35K) + PLAN.md(1516行·~35K)
     设计报告合计: ~112K (其中~80%为推理/自检/设计依据·非审计所需)
     新(YAML): 4个.yml文件合计 ~20K
     节省: ~92K

  2. Storyboard Planner (旧: 设计报告完整MD ~73K)
     读取: 三Agent设计报告MD(3,466行·~73K) + ANCHOR_BASELINE(~4K)
     新(YAML): 3个.yml + ANCHOR_BASELINE.md = ~9K + ~4K = ~13K
     节省: ~64K (注: ANCHOR_BASELINE仍是MD·不属于YAML化范围)

  3. Prompt Composer (旧: PLAN + 设计报告 ~120K)
     读取: PLAN.md(1516行·~35K) + 三Agent设计报告MD(3,466行·~77K) + 其他(~8K)
     新(YAML): PLAN.yml(~8K) + 3个.yml(~9K) + 台本上下文(~25K)
     新总计: ~42K
     节省: ~78K

直接节省合计: 92K + 64K + 78K = ~234K
```

**假设:**
1. 设计Agent愿遵守双文件输出规范 (.md+.yml)
2. YAML schema覆盖下游Agent所需全部结构化字段 (见yaml_only_spec §4)
3. 台本本体(【生成指令】逐秒描述)无法YAML化·仍需~25K (已在计算中保留)
4. 审计Agent正确配置为只读.yml·不fallback到.md
5. SDA/SSA如作为独立Agent也受益·但scene_auditor合并后已计入Scene Auditor

## 3. 修复间重叠分析

四个修复并非独立并行的优化——它们作用于同一管道的不同环节·存在两类重叠:

### 3.1 识别到的重叠

| 重叠对 | 重叠量 | 性质 | 说明 |
|:---:|:---:|------|------|
| **A-B** | ~30K | 共享文件中的KB内容 | P-CONSTITUTION在旧管道中被Fix A的"共享上下文"和Fix B的"KB文件组"双重计入。Quick ref已含宪法压缩版·Context package不再需要单独包含宪法 |
| **A-D** | ~20K | 审计Agent的共享上下文 | 审计Agent在旧管道中既加载共享文件(被Fix A消除)·又读取上游完整报告(被Fix D消除)。AB间计数有交叉 |
| **B-D** | ~15K | KB引用在设计报告中的传播 | 设计报告中的KB规则ID引用在YAML化后仍在.yml中(结构化字段)·但Fix B的quick ref已含这些规则摘要·下游不再需要从设计报告中理解KB规则——但不能双重计入节省 |
| **C-D** | ~50K | SSA的Gate 0与输入读取 | Fix C消除SSA的Gate 0处理(~60K)·Fix D减少SSA的输入读取(~92K)。两者都降低SSA的177K总量。但合并后SSA从177K→约65K(节省112K)·而非60K+92K=152K·重叠约40K |
| **A-C** | ~5K | Scene Auditor Phase 0调用 | Phase 0移至调度器·Scene Auditor不再读Gate 0规则文件(原本在共享上下文中)。微量重叠 |
| **B-C** | ~5K | Gate 0正则规则在KB中的引用 | KB规则中有Gate 0检测方法说明·两种优化均可减少其加载。极微量 |

**总重叠: ~125K** (取各重叠中位数合计)

### 3.2 合并计算

```
独立现实合计: 196K + 230K + 78K + 234K = 738K
扣除重叠:     738K - 125K = 613K

但 Token Forensics 报告确认: 
  纯浪费 395K + 低效 239K = 634K (最大可节省)

613K < 634K → 在物理上限内 ✓

微调: 613K ≈ 634K的96.7% → 基本消除了几乎所有可消除浪费
这过于乐观——四个修复仅覆盖10项浪费中的4-5项。
```

### 3.3 现实修正

回顾浪费报告§4: 10项可立即消除浪费合计 ~680-850K。四个修复方案涵盖其中:
- Fix A+B: 浪费#4(KB加载·150-300K) + #7(宪法重复·15-25K)
- Fix C: 浪费#3(Gate 0·~175K) + #8(禁止清单LLM·3-5K)
- Fix D: 鱼骨图中"上游输出膨胀"部分(非单项编号)

四个修复**未涵盖**的浪费:
- #1 Movement Designer静态辩护: ~35K
- #2 SDA Phase 1 S-Level执行: ~25-144K
- #5 OBJECT_TIMELINE S-Level跳过: 间接
- #6 Storyboard Planner TIME_SKELETON: ~136K
- #9 S-Level设计依据块: ~5-8K
- #10 单场景锚点审计: ~137K + 2 Agent

未涵盖浪费合计: ~200-460K。即使四个修复完美执行·这些浪费仍存在。

### 3.4 最终三档联合估算

| 档位 | A | B | C | D | 独立和 | 重叠 | 联合节省 | 新管道 | 节省% |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **保守** | 125K | 160K | 35K | 160K | 480K | -100K | **380K** | 495K | 43.4% |
| **现实** | 196K | 230K | 78K | 234K | 738K | -125K | **470K** | 405K | 53.7% |
| **乐观** | 300K | 300K | 145K | 280K | 1025K | -200K | **550K** | 325K | 62.9% |

**现实档校准依据:**
- 470K < 634K(可消除上限) ✓ (留有164K未消除浪费·对应未覆盖的6项)
- 470K ≈ 395K(纯浪费)的100% 覆盖 + 239K(低效)的31% 覆盖 → 消除了全部纯浪费和约1/3低效浪费 → 合理
- 新管道405K: 保留合理的242K + 剩余低效~75K + 未覆盖纯浪费~88K = ~405K ✓

## 7. 风险与警告

### 7.1 验证风险

1. **Quick ref 覆盖不全风险**: 若15K quick ref遗漏Agent决策所需的关键KB规则 → 深读触发率飙升(>3次/场景) → Fix B节省从230K降至150K以下。缓解: 路由覆盖验证+场景类型矩阵测试。

2. **CONTEXT_PACKAGE 信息不足风险**: 若8K包过度精简导致Agent频繁深读原始文件 → Fix A节省减少30-50%。缓解: §3.4深读索引+Agent"先速查后深读"纪律。

3. **YAML schema 不完整风险**: 若.yml缺少审计Agent需要的字段 → 审计Agent回退读取.md → Fix D节省归零。缓解: schema与各Agent指令文件交叉验证。

4. **Gate 0 正则遗漏风险**: 若台本格式变异导致区块解析失败 → 回退v1.0全局扫描 → 假阳性回归。缓解: 3.3.1回退机制+格式标准化。

### 7.2 交互风险

5. **四修复叠加的兼容性**: Fix A的package中嵌入Fix B的quick_ref → 若quick_ref更新·package需重新生成。缓解: Step 0.7A自动获取最新quick_ref。

6. **Agent指令修改遗漏**: 4个修复共需修改7+个Agent指令文件(删除旧Read清单·新增package/YAML读取)。若有遗漏→旧行为和新行为并存→浪费未消除。缓解: 实施清单(各spec §7)。

### 7.3 基线漂移风险

7. **场景复杂度分布变化**: 若未来场景偏C-Level→四个修复的节省比例不变·但绝对值可能更大(因为有更多Agent受益)。对ROI有利。

8. **新Agent引入**: 若管道新增Agent→需确保新Agent遵守新协议(YAML-only·读package非原始文件)。否则新增Agent制造新浪费。
