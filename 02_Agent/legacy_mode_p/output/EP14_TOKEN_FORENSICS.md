## 1. 逐Agent浪费归因

### 归因方法论

每个Agent的token消耗分解为五个来源:

| 来源 | 定义 | 估算方法 |
|------|------|---------|
| **上下文加载** | Read工具调用读取文件的总token | 文件大小 × 被读取次数(含子集/片段Read) |
| **KB加载** | 03_导演知识库_v5.0.md被读取的部分 | 167,622字节(~42K tokens)/完整读取·按路由子集估算 |
| **上游重读** | 审计Agent读取设计Agent完整输出(含推理) | 上游输出文件大小 × 读取次数 |
| **重复信息** | 同一空间描述/宪法条文/P-STATE条目跨文件重复 | 跨文件重叠内容估算 |
| **净推理** | 产生独特价值的token | 总数 - 前四项合计 |

> **Token换算公式:** 中英混合文本约3.5字符/token(实测·导演系统技术文档·中文占比~60%)。中文纯文本约1.5-2字符/token。本报告保守采用 **4字符/token** (中文主导·含代码块/ascii-art)。

**浪费诊断:** 新版Scene Auditor整合了SDA+SSA+Storyboard Planner审计功能为四阶段单Agent, token效率(173K vs 旧管道审计457K)提升了62%。但仍有明显浪费:

## 6. 方法论备注

### 6.1 Token估算方法

本报告采用: **4字符/token** (中英混合技术文档·中文~60%占比·含代码块/mermaid/ascii-art)。

实际Claude API token计数与本估算的误差范围: ±15%。建议后续使用Anthropic官方Token Counting API精确测量。

### 6.2 本报告的局限性

1. **KB路由估算基于平均采样:** 实际每个Agent的KB路由子集可能与本报告估算的350-500条有差异。

2. **LLM推理token不可直接测量:** "净推理"估算为总数减去可归因部分——可能低估(部分"上下文加载"token也参与了推理)。

3. **新架构数据为单场景(EP14 S1·案情室):** 多场景(如EP14全部3场景)的浪费比例可能不同——Scene Auditor的上下文加载占比在多场景中可能降低(共享文件只需加载一次·设计报告逐场景不同)。

4. **未计入API往返开销:** Tool Use API调用本身的元数据token(非文件内容)未纳入计算。
