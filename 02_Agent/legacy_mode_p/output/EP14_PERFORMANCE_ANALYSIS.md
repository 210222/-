### 2.2 并行度与墙钟分析

所有Agent均为串行执行(或依赖链约束)，因此:

```
wall-clock_旧管道 = Σ(7 Agent耗时) = 3,475,826ms ≈ 57.9分钟
wall-clock_新架构设计 = Σ(5 Agent耗时) = 1,637,036ms ≈ 27.3分钟
wall-clock_新架构执行 = 636,874ms ≈ 10.6分钟
```

**最长单Agent耗时占主导:**
- 旧管道中Composition Designer(24.3分钟)占管道总耗时的42%
- 即使将其余6个Agent完全并行化，wall-clock也只能降至 24.3分钟(从57.9分钟)，改善57%
- 新架构中Scene Auditor v1.0(10.6分钟)是执行阶段唯一Agent，无并行空间

### 2.3 瓶颈本质

```
瓶颈 = 单Agent最大耗时 / 总wall-clock

旧管道瓶颈度 = 24.3 / 57.9 = 42.0% (Composition Designer)
新架构执行瓶颈度 = 10.6 / 10.6 = 100% (唯一Agent, 无瓶颈概念)
```

**结论: Composition Designer是旧管道的绝对瓶颈。新架构通过合并多个Agent的功能到单一Scene Auditor，消除了多Agent间的串行等待，但也失去了并行化可能性。当前10.6分钟/场景的执行时间是合理的单Agent耗时。**

## 5. 推理过程过长根因+解决方案

### 5.1 根因分析

**现象:**
- Composition Designer: 1,457秒(24.3分钟), 33次工具调用
- 第一次红队审计: 1,270秒(21.2分钟), 12次工具调用
- Scene Auditor v1.0: 637秒(10.6分钟), 工具调用未记录

**根因层次:**

```
Layer 1: 上下文加载 (占60-70%耗时)
  ├── 读取KB v5.0 (~720条规则, 每次Read触发LLM再处理)
  ├── 读取上游Agent全部输出(每个输出500-1600行)
  └── 读取项目指令文件(CLAUDE.md, scene_level, scene_prompt)

Layer 2: 推理深度 (占20-30%耗时)
  ├── 逐条比对KB规则 vs 实际输出
  ├── 多阶段推理(如Scene Auditor的四阶段)
  └── 自检循环(Agent反复验证自己的输出)

Layer 3: 系统开销 (占5-10%耗时)
  ├── 网络延迟(API往返)
  ├── 输出生成(Write工具调用)
  └── Token化/反Token化
```

**核心矛盾:**
每个Agent需要读取大量上下文(KB规则、指令、上游输出)才能开始工作。每次`Read`工具调用意味着一次完整的LLM推理循环(读取→理解→决策→下一工具调用)。文件越大，单次Read的token消耗和处理时间越长。

以Composition Designer为例:
```
33次工具调用 ÷ 1,457秒 = 平均44秒/调用
其中估计: 
  - 10次读取大文件(KB, 上游输出): 每次60-90秒
  - 5次读取小文件(指令片段): 每次20-30秒
  - 18次推理+写入: 每次25-40秒
```

### 5.2 解决方案

#### 方案A: 预编译上下文 (高优先级)

```
当前:
  Agent启动 → Read KB(720条规则, 完整文件) → Read指令 → Read上游输出 → 开始工作

优化后:
  Agent启动 → Read 预编译摘要(200条相关规则, 已过滤) → 快速进入核心推理
  
实现:
  1. 在管道前端增加"上下文编译器"Agent(一次性成本)
  2. 为每个下游Agent生成定制化上下文摘要
  3. 摘要格式: 只有与该Agent职责相关的规则+上游输出关键字段
  
预估效果:
  - 上下文加载时间: 减少60-70%
  - 单Agent token: 减少30-50%
  - Composition Designer: 1,457秒 → 预计600-800秒
```

#### 方案B: 规则分层加载 (中优先级)

```
当前: KB v5.0 单一文件, ~720条规则

优化:
  L1_核心规则 (50条): 所有Agent必须遵循的硬约束
  L2_场景规则 (100条): 仅特定场景类型需要的规则
  L3_细节规则 (570条): 按需查阅的参考规则
  
Agent默认只加载L1, 按需加载L2/L3
```

#### 方案C: 限制推理深度 (低优先级)

```
当前: 无推理深度上限
优化: 在Agent prompt中设置:
  - 最大工具调用次数: 20次
  - 最大推理步骤: 15步
  - 超时自动提交当前最佳结果
  
风险: 可能在复杂场景中过早截断
```

#### 方案D: 审计输出模板化 (中优先级)

```
当前: Scene Auditor自由格式四阶段审计报告
优化: 
  阶段1(兼容性): 填表式检查 [PASS/FAIL/WARN] × N项
  阶段2(连续性): 填表式检查 [PASS/FAIL/WARN] × N项
  阶段3(TIME_SKELETON diff): 结构化diff格式
  阶段4(最终判断): 自由文本(仅在有FAIL时展开)
  
效果: 减少输出token 173K→100K (42%减少)
      减少推理时间 637s→400s (37%减少)
```

### 5.3 优先级排序

| 优先级 | 方案 | 预估收益 | 实施成本 | 风险 |
|:------:|------|--------:|:------:|:---:|
| P0 | 方案A: 预编译上下文 | Token -40%, 时间 -50% | 中(需新建上下文编译器) | 低 |
| P1 | 方案B: 规则分层 | Token -25%, 时间 -30% | 低(重构KB文件) | 低 |
| P2 | 方案D: 审计模板化 | Token -42%, 时间 -37% | 低(修改Scene Auditor prompt) | 中(可能遗漏边缘case) |
| P3 | 方案C: 推理深度限制 | 时间 -30% | 低(修改prompt) | 高(可能过早截断) |

## 综合建议

### 短期(下个迭代·EP15)

1. **立即实施规则分层(方案B):** 将KB v5.0拆分为L1/L2/L3三层。这是成本最低、风险最小的优化, 预计节省25%上下文token。

2. **Scene Auditor输出模板化(方案D):** 将自由格式四阶段审计报告改为结构化填表+自由评论混合格式。当前173K/token的输出包含了大量冗余叙述。

3. **移除假阳性触发逻辑:** Scene Auditor v1.0报告的1个阻断为假阳性——说明其判断阈值过于激进。调整prompt中的阻断判定标准, 减少误报。

### 中期(EP16-EP18)

4. **开发上下文编译器(方案A):** 这是ROI最高的优化——预计可将单Agent耗时减半。需要一个"上下文编译"Agent, 在管道启动时为每个下游Agent生成定制化上下文摘要。

5. **量化新架构下Storyboard Planner和Prompt Composer的去向:** 当前分析中, 旧管道这两个Agent(共254K tokens)的功能在新架构中的映射不明确。需要确认它们是被合并入Scene Auditor还是保留为独立Agent。

6. **多场景基准测试:** 在EP15/16中执行2-3个场景, 收集新架构的多场景性能数据, 验证4.3节的预估模型。

### 长期(架构演进)

7. **探索"设计即执行"模式:** 当前新架构仍有"设计阶段→执行阶段"两阶段分离。如果Scene Designer能直接输出可执行规则(而非自然语言指令), 则可以消除128K tokens的执行层Agent。

8. **建立Agent性能监控面板:** 为每个Agent记录: tokens, wall-clock, 工具调用次数, 阻断/警告/通过数量, 假阳性率。这些数据将驱动后续优化决策。

9. **考虑混合架构:** 在简单场景(如EP14场景A·静态对话)使用新架构(1 Agent), 在复杂场景(如EP14场景C·动作场景)使用旧架构(7 Agent并行), 根据Complexity Router的分类结果动态选择管道。
