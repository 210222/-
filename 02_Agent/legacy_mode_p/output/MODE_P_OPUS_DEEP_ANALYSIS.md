## 1.1 追踪目标A：案情室空间描述（6m×4m×3m·白板北墙·格栅灯5000K）

### 第一次出现：Step 0 IMAGE_AUDIT（调度器自执行）

这是信息的**出生地**。调度器在 Step 0 图片资源盘点时，从场景参考图（九宫格）的逐格文本标注中提取出空间事实。此时的信息最完整——包含尺寸（6m×4m×3m）、墙面特征（白板北墙）、灯光（格栅灯5000K）、地板材质、门窗位置、可放置区域。

**信息状态:** 原始·完整·含LLM推理产生的空间推断（某些尺寸是从参考图"读"出来的，可能存在误差）
**成本:** ~2K tokens（包含在 IMAGE_AUDIT 报告中）

### 第二次出现：ANCHOR_BASELINE §C 空间坐标系（Step 0.6）

调度器从 IMAGE_AUDIT 提取空间信息，写入 ANCHOR_BASELINE.md §C。此时做了一次**格式化转换**——从"九宫格文本标注"转为"空间坐标系"（纵深×宽度×高度·可放置区域坐标·禁入区标记·光源锚点）。

**新增信息:** 空间坐标系（坐标化）、可放置区域编号①②③、禁入区标注
**重复信息:** 6m×4m×3m、白板北墙、格栅灯5000K — 全部是重复
**成本:** ~500 tokens

### 第三次出现：Shot Architect 机位设计报告（C-Level Step A2.1）

Shot Architect 在 "Step 0: 场景类型判定+空间描述" 中重新写了一遍空间描述。

**新增信息:** 零。Shot Architect 唯一的新增是机位选择和覆盖策略
**重复信息:** 整个空间描述块被完整复制——尺寸、墙面、灯光、可放置区域
**成本:** ~800 tokens（空间描述部分）
**必要性:** ❌ 完全可以引用 ANCHOR_BASELINE §C 或通过 CONTEXT_PACKAGE 获取

### 第四次出现：Movement Designer 运镜设计报告（C-Level Step A2.2）

Movement Designer 在输入中读了 Shot Architect 的完整报告（包含空间描述），然后在自己的报告中又写了一遍空间描述。

**新增信息:** 零。Movement Designer 的新增只有运镜参数
**重复信息:** 空间描述从头到尾又抄了一遍
**成本:** ~800 tokens
**必要性:** ❌ Movement Designer 只需要知道空间尺寸来验证运镜可行性，不需要整段空间描述

### 第五次出现：Composition Designer 构图光影报告（C-Level Step A2.3）

Composition Designer 读了 Shot + Movement 两份报告，然后自己的报告中又包含空间描述。

**新增信息:** 零。Composition Designer 的新增是构图参数和光影方案
**重复信息:** 空间描述第三次在 Agent 报告中被完整复制
**成本:** ~800 tokens
**必要性:** ❌ 同样只需要尺寸和光源位置，不需要整段描述

### 第六次出现：Scene Design Auditor（SDA）审计报告

SDA 读了三份设计报告（每份都包含空间描述）。SDA 的输出中包含"空间可行性验证"部分——又描述了一遍空间。

**新增信息:** 空间可行性验证结论（"全部机位在可放置区域内"）
**重复信息:** 空间事实描述（尺寸、墙面、灯光）
**成本:** ~500 tokens
**必要性:** ⚠️ 验证结论需要引用空间事实，但不需要完整复制描述

### 第七次出现：Scene Script Auditor（SSA）审计报告

SSA 读了台本（台本包含 C2 Environment Anchor 中的空间摘要），在审计报告中又引用了一次。

**新增信息:** 零引用结论（"场景结构与参考图一致"）
**重复信息:** 空间描述片段
**成本:** ~300 tokens
**必要性:** ❌ 引用结论不需要重复空间事实

### 第八次出现：Prompt Composer 导演台本（Step A3）

台本的场景级共享锚点（C2 Environment Anchor）中包含经过 storyboard_planner 提取的空间摘要。

**新增信息:** 格式化后的锚点描述（从 PLAN 骨架逐字复制）
**重复信息:** 空间摘要（已精简，但仍是从 IMAGE_AUDIT 开始第8次出现）
**成本:** ~200 tokens

### 第九次出现：Render Packager RENDER_PACKAGE.md（Step 9.5）

台本中的 C2 Environment Anchor 原样保留。

**新增信息:** 零
**重复信息:** 同第八次
**成本:** ~200 tokens（包含在台本中，非独立）

| 6 | RENDER_PACKAGE C1 | 保留台本内容 | ✅必要 |
| 7 | P-Verifier 结构同构验证 | 作为比对基准引用 | ✅必要·验证需要 |

**关键问题:** 7次引用中，如果任何一次有措辞偏移（哪怕一个同义词替换），P-FAL-05（身份漂移）就会触发。社区经验表明，"深棕短发"和"深棕色短发"在Seko眼中是两个人。

**浪费诊断:** 7次×~200 tokens = ~1,400 tokens。如果统一通过 TIME_SKELETON.global_anchors 一个源头分发，可以降到1次写入+6次引用指针。

**v6.2 改进:** CONTEXT_PACKAGE 方案设计通过 §4 角色锚点摘要和深读索引来解决此问题——但当前尚未部署。

## 3.1 当前 MODE:P 管道最浪费的三个地方

### 浪费#1：审计比设计还重

**当前做什么：** 在每个场景中，审计Agent（SDA+SSA/Scene Auditor）消耗的token比设计Agent（Shot+Movement+Composition/Scene Designer）更多。EP14数据显示审计占36.7%（321K tokens），设计占34.3%（300K tokens）。审计/设计比=1.07:1。

**为什么浪费：** 这相当于**你请了三个最贵的厨师来做一桌菜，然后又请了三个更贵的品鉴师来鉴定这桌菜有没有毒——结果品鉴师花的钱比厨师还多**。在一个理性的生产流程中，检查环节应该比生产环节轻量——检查一块手表比造一块手表快得多。但这里反过来了。

SDA产出1,040行报告，零阻断发现，10项警告中5-6项可用正则检测。SSA产出504行，3项阻断全部是正则可检测问题（过程动词、时间模糊词、工程符号）。这两个审计Agent加起来321K tokens，但真正的LLM增量价值不到30%。

**怎么改：** Gate 0前置已经设计了——正则扫描在审计Agent之前运行，过滤掉所有可确定性检测的问题。如果Gate 0全部通过，审计Agent降级为只做Phase 1-3中需要LLM判断的~30%部分。v6.2 Scene Auditor的四阶段设计已实现此方案，但尚未部署。

### 浪费#2：每个 Agent 都在读全套公共文件

| F5 运镜 | false | false | 通过 |

→ **判定：🟢 S-Level**（应使用2 Agent管道）

### 实际状态：被卡住

EP14架构浪费报告明确写了：
> "复杂度路由未激活（新架构尚未部署）。complexity_router将EP14A正确分类为S-Level，但4个阻断项（BLOCK-1~4）未修复，S-Level不可用。当前实际运行的是C-Level全管道（~18 Agent）。根因解决停留在概念，实现未完成。"

**卡在哪里：**

**占了多少篇幅？** 旧管道中三Agent设计报告共3,466行，其中【设计依据】块约占800-1,000行（约25%）。Shot Architect ~50行·Movement Designer ~100行·Composition Designer ~200行三Agent各自的KB引用+论证全文。

**必要性判定：❌ 形式主义——Agent间的信息隔离使得下游无人能读它**

render_packager_v1.0.md §2.1 明确写了："【设计依据】块是prompt_composer Step 2D写入的KB规则ID引用……Seko渲染引擎不需要知道为什么这么拍——它只需要知道怎么拍。"然后直接删除了它。

**建议：** 不要在台本中写入【设计依据】。KB规则ID引用应在Agent设计报告中保留（供审计Agent Phase 1验证），但不进入导演台本。render_packager的删除操作本身也消耗token——不生成就不需要删除。

## 3.6 v7.0 架构建议：两段式管道 + 确定性与概率性分离

如果用导演能懂的语言来描述——

### 当前问题：一部电影拍了两个版本

现在的 MODE:P 相当于：**你每拍一场戏，都请了全套剧组（摄影、灯光、美术、剪辑、音效）来拍，然后又请了另一套人马来检查——而这两套人马花的钱差不多**。但对一场简单的室内对话戏（1个房间·2个人·4句对白），你只需要一个导演+一个摄影师就够了。

### v7.0 推荐结构

```
第一阶段：确定性管道（Deterministic Pipeline）—— "预制阶段"
  做什么：所有能确定的事情，在 Agent 启动之前就做完
  谁做：调度器（Orchestrator）自执行·零LLM

  Step 0.5: 复杂度判定（F1-F7提取） → S/M/C级分类
  Step 0.6: Gate 0 正则扫描 → 台本格式门禁
  Step 0.7: CONTEXT_PACKAGE 编译 → 公共上下文一次生成
  Step 0.8: KB_SUMMARY 预提取 → 规则摘要替代完整KB

  产出：场景上下文包（~23K tokens）+ KB规则摘要（~10K tokens）
  门禁：任何🛑 → 不进入第二阶段

第二阶段：概率性管道（Probabilistic Pipeline）—— "创作阶段"
  做什么：LLM 只做 LLM 擅长的事（机位选择·运镜设计·构图审美）
  谁做：Agent（独立LLM调用）

  S-Level（2 Agent）:
    Agent 1: Scene Designer（三合一设计+台本）
    Agent 2: Scene Auditor（四合一审计）
  
  M-Level（4-6 Agent）:
    Agent 1: Scene Designer（二合一）
    Agent 2: Movement Designer
    Agent 3: Scene Auditor
    Agent 4: Storyboard Planner（条件）
    Agent 5: Prompt Composer（条件）

  C-Level（完整管道）:
    保持当前完整结构

  核心规则：每个Agent只调用1次LLM（不允许多轮对话）+ 不加载任何公共文件
  （公共文件已在第一阶段预编译到上下文中）
```

### 为什么这样更好

**类比：拍电影的两个阶段**

**第一阶段（确定性）** 相当于**前期筹备**——找场地、定演员、排通告。这些事情一旦确定，全剧组都按同一个时间表工作，不需要每人各查一遍通告单。

**第二阶段（概率性）** 相当于**实拍**——导演、摄影、灯光各自发挥创作力，但都基于同一个场地（空间地图）、同一批演员（Character Anchor）、同一套规则（KB规则）。

**当前的问题**是：筹备和实拍混在一起，每个部门在进场前都要自己重新调查一遍场地。

### 关键区别

| 当前架构 | v7.0 建议 |
|---------|----------|
| 每个Agent加载全套公共文件 | 调度器预编译一次·所有Agent共享 |
| 审计比设计还重 | 确定性检查全部前置·审计只做LLM必需的部分 |
| 复杂度路由未生效 | S/M/C在管道入口决定·不进入场景循环 |
| 形式主义论证 | "什么都不做"不需要辩护 |
| Agent输出含设计依据→被下游删除 | 不生成设计依据→节省生成+删除的成本 |
