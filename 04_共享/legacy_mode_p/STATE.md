## §3: Open Failures (未解决失败 · FSRS追踪)

> **目的:** 追踪MODE:A管道中已识别但尚无可靠解决方案的失败模式。FSRS-6信号管理。
> **更新触发:** postcheck发现新失败模式·MODE:F反馈注入·同一模式复现更新FSRS信号。
> **使用方式:** 每次MODE:A启动时Read本段·主动规避已知失败模式。

```
格式: [FAL-XX] | 失败描述 | 触发条件 | FSRS(S/D/R) | 复现次数 | 状态
FSRS: Stability(S) / Difficulty(D·1-10) / Retrievability(R)
状态: 🔴未解决 / 🟡部分解决 / 🟢已解决(待迁移到§2) / ⚫已失活(R<0.2)

FSRS power-law:
  复现 → S增长(1.0→2.5→6.0→14.0…)
  不复现 → R自然下降
  S≥10 + 复现≥5次 → 🔴高优先级蒸馏
  S≥6 + 复现≥3次 → 🟡中优先级蒸馏
  S<6 或 复现<3次 → ⚪观察中·不触发蒸馏
  R<0.2 → 信号失活·移出活跃追踪
```

## 维护规则

```
1. 自动更新: postcheck每次完成验证后自动追加§5会话日志
2. 人工审核: 每10次MODE:A运行后人工审查§1-§4·确认/修正/迁移条目
3. 升级规则:
   ┌─ §4 教训≥3条同类 → 触发 Investigate → 升级为 §3 失败模式
   ├─ §3 失败模式找到可靠修复 → 影子测试 → 升级为 §2 候选规则
   ├─ §2 候选规则人工确认 → 合并到KB → 迁移到 §1 已验证事实
   ├─ §1 事实在新版LLM上失效 → 降级到 §3 失败模式
   └─ §3 FSRS R<0.2 → 标记⚫已失活·移出活跃追踪
4. 与MODE:F联动:
   └─ MODE:F用户反馈 → 提取失败模式 → 更新§3(FSRS信号注入)
5. 与MODE:R联动:
   └─ MODE:R离线体检 → 发现系统性缺陷 → 更新§3 + 触发distillation_engine批量Investigate
6. 与distillation_engine联动:
   └─ §2候选规则积累到阈值(≥3条) → 触发Consult(人工确认)
   └─ §3 FSRS S≥6 + 复现≥3次 → 触发Investigate(根因分析)
7. 与P-STATE联动:
   └─ STATE.md(MODE:A) 和 P-STATE.md(MODE:P) 独立维护
   └─ 跨模式模式识别: 同一失败在STATE和P-STATE同时出现 → 标记为"跨管道系统性缺陷"
   └─ 跨管道缺陷 → 优先蒸馏(提升一个优先级)
```
