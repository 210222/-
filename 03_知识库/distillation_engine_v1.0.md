# 知识蒸馏引擎 v1.0 — Fail→Investigate→Verify→Distill→Consult

> **版本**: v1.0 · 2026-06-28
> **设计依据**: Fable 5 五阶段学习循环 + FSRS-6 衰减 + 导演系统场记库
> **定位**: 研究空白自研 — 当前学术界无可参考的知识蒸馏方案
> **触发**: 每次MODE:A完成·每10次MODE:A自动蒸馏·MODE:F信号触发
> **输出**: 候选规则 → 人工确认 → KB追加

---

# 设计原理

```
学术界现状 (Deep Research 2026):
  "没有发现任何关于知识蒸馏或持续学习的研究"
  
我们的解决方案:
  Fable 5 STATE.md (五段记忆) 
    + FSRS-6 power-law衰减 (反馈信号管理)
    + 导演系统场记库 (实例级状态追踪)
    + 人工确认闸门 (防止规则膨胀)

核心洞察:
  不是"自动从数据学习" (学术界未解决)
  而是"系统性积累·周期性蒸馏·人工确认" (工程可行)
```

# ① Fail — 发现新问题

```
触发: 每次MODE:A管道完成
输入: Verifier v2.0 报告 + postcheck 报告 + enhance 输出

记录三类"失败":

  A. 阻断失败 (🛑): 
     Verifier/Postcheck 阻断 → 返工后仍未解决
     → 记录到 STATE.md §3 Open Failures

  B. 表面修复 (⚠️):
     Verifier Skeptic 检测到的标注修复但未实质解决
     → 记录到 STATE.md §4 Lessons Learned

  C. 新增缺陷 (🟡):
     Verifier Researcher 检测到的增强引入的新问题
     → 记录到 STATE.md §4 Lessons Learned

过滤: 
  - 单次偶发问题 → 仅记录·不触发蒸馏
  - 同一模式出现 ≥3次 → 触发 Investigate
```

# ② Investigate — 分析根因

```
触发: 同一失败模式出现 ≥3次
输入: STATE.md §3 Open Failures + §4 Lessons Learned

分析维度:

  1. 是知识缺失吗?
     □ KB中没有相关规则 → 缺失型失败
     □ KB中有但未被路由到 → 路由型失败
     □ KB中有但规则不够具体 → 精度型失败

  2. 是执行偏差吗?
     □ enhance 没有遵守规则 → 合规型失败
     □ Verifier 没有检测到 → 验证型失败
     □ LLM 理解偏差 → 语义型失败

  3. 是冲突未解决吗?
     □ 两条规则给出矛盾建议 → 冲突型失败
     □ 规则与用户意图矛盾 → 意图型失败

输出: 根因分类 + 建议修复方向
```

# ③ Verify — 影子测试

```
触发: Investigate 产出候选修复方案
方法: 影子测试 (Shadow Testing)

流程:
  1. 准备影子数据集:
     收集该失败模式出现过的历史剧本分镜 (≥3个)
     
  2. 并行运行:
     A线: 当前规则集 (旧)
     B线: 候选修复后规则集 (新)
     同一剧本 → 两个版本 → 对比

  3. 验证标准:
     ✅ B线解决了该失败模式
     ✅ B线没有引入新的 🛑 或 ≥3个 ⚠️
     ✅ B线的增强质量不低于A线 (postcheck评分)
     
  4. 通过 → 进入 Distill
     不通过 → 回到 Investigate 修正

  影子测试预算:
     ≤5个分镜的微型测试 (防止消耗过多API)
     仅测试受影响的场景类型 (按KB Index v2.0路由)
```

# ⑤ Consult — 人工确认

```
触发: 累积 ≥3个候选规则 或 每10次MODE:A运行
输出: 更新后KB规则文件

流程:
  1. 输出候选规则清单
  2. 对每个候选规则:
     
     确认选项:
     □ 接受 → 正式写入KB规则文件
     □ 接受但修改 → 调整后写入
     □ 拒绝 → 标注原因·不写入
     □ 合并 → 与现有规则合并
     
  3. 写入KB:
     按场景类型归入对应章节
     分配规则ID (延续现有编号体系)
     更新 kb_index_v2.0.md 规则量计数
     
  4. 清理:
     将已确认规则从 STATE.md §2 移动到 §1 Verified Facts
     更新 §5 Last Session 摘要

人工确认是系统的安全闸门:
  防止低质量规则自动写入KB
  防止规则膨胀 (每个候选规则需明确解决问题)
```

# FSRS-6 反馈信号管理

```
每集 MODE:A 完成后:

  所有反馈信号带时间戳:
    Stability (S): 信号强度·初始=1.0
    Difficulty (D): 修复难度·1-10
    Retrievability (R): 信号可检索性
    
  FSRS-6 power-law 衰减:
    复现 → S增长 (1.0→2.5→6.0→14.0...)
    不复现 → R自然下降
    当 R < 0.2 → 信号失活·移出活跃追踪
    
  信号优先级:
    S≥10 + 复现≥5次 → 🔴 高优先级蒸馏
    S≥6 + 复现≥3次 → 🟡 中优先级蒸馏
    S<6 或 复现<3次 → ⚪ 观察中·不触发蒸馏
```
