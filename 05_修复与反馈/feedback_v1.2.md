## 第二步：更新反馈日志（v1.2：FSRS-6 衰减）

每条反馈带时间戳。规则不固定过期——用 FSRS-6 power-law 衰减。

```
📊 反馈日志 · EP [X] · [YYYY-MM-DD]

本轮: [N]镜检测·[P]通过·[F]失败

失败明细（每条带时间戳·Stability初始值=1.0）:
  #2 ⚠️ 首帧跳变 · S=1.0 · [2026-06-15]
  #3 ❌ 面部变形 · S=1.0 · [2026-06-15]
  #5 ⚠️ 家具偏移 · S=1.0 · [2026-06-15]

FSRS-6 衰减规则:
  - 每集复现 → Stability增长（1.0→2.5→6.0→14.0...）
  - 不复现 → Retrievability自然下降
  - 1次确认≈9天可检索 / 5次确认≈74天 / 20次≈13个月
  - 无人提及28天→不会消失·但权重显著降低
  - 成功信号1.5x权重（修复确认=比失败更稀有）

累积统计（全剧）:
  EP1→EP2→...→EPN 首帧正确率趋势
  最高失败类型及FSRS状态
```

## 🆕 第二步·B面：五阶段验证循环 (v4.2 · 借鉴Fable 5 STATE.md)

每次postcheck发现缺陷后，按以下阶段推进:

  阶段1 · 记录失败 (Fail):
    将缺陷写入反馈日志·标注时间戳+审计编号+分镜号
    
  阶段2 · 调查根因 (Investigate):
    诊断为什么修复失败——是规则不够精确？还是enhance执行偏差？
    
  阶段3 · 验证假设 (Verify):
    将猜测转化为已验证的事实——在下一次MODE:A运行中确认修复是否有效
    📊 验证覆盖率目标: ≥70%（Fable 5基准: 73%）
    
  阶段4 · 蒸馏规则 (Distill):
    将已验证的修复模式蒸馏为通用规则→补充到KB或FIX手册
    
  阶段5 · 下次查阅 (Consult):
    下一集MODE:A启动时·优先查阅已蒸馏的规则

🆕 验证状态追踪:
  每轮MODE:A运行后更新:
    已验证事实: [N]条 · 通用规则: [M]条 · 开放失败: [P]条 · 已蒸馏: [Q]条

## 第四步：规则升级（v1.2：影子测试门控 + Git回滚）

**当前不可直接改文件。必须先过影子测试。**

```
🔧 规则升级提案 #N

触发: [失败类型]≥[N]次·跨[M]集
根因: [___]
升级: [目标文件·目标章节]

步骤1: 影子测试（自动）
  1. 取出最近3集的反馈日志
  2. 用新规则模拟审计这3集
  3. 对比旧规则:
     ✅ 新规则修复了至少2个旧规则的漏检/误报 → 通过
     ❌ 新规则引入新错误或破坏已有通过项 → 阻断

步骤2: 3法官验证（自动）
  3个独立LLM评委各自评估:
    - 新规则是否逻辑自洽？
    - 新规则是否与已有规则冲突？（WIRE: 64.6%的规则集存在内部冲突）
    - 新规则是否过于特化？（仅适用于触发它的那3个案例·不通用→拒绝）
  2/3法官通过→进入步骤3

步骤3: 用户确认
  展示: 影子测试结果 + 3法官投票 + 建议的Git commit message
  询问: 是否应用？[Y/N]
  
步骤4: Git提交 + 可回滚
  Y → agent直接编辑文件 → git commit: "🔧 规则升级#[N]: [摘要]"
  如果升级后下集表现退化 → git revert + 规则标记为"已回滚·需重新设计"

VIGIL原则（核心身份不可变·v2.0扩展）:
  enhance的核心框架(一层WHY·二层HOW主线·四层DELIVER骨架)不能被动
  允许修改:
    - 三层GUARD的具体约束·首帧锁定规则细节·负面约束表条目
    - 🆕 director_agent 审计11-15的具体阈值和基线(如最小覆盖计数/偏差阈值/两极分化阈值)
    - 🆕 director_fix_playbook 中FIX-11~FIX-15的修复方案参数
    - 🆕 知识库§11-§15中规则的具体数值和阈值(如COV覆盖机位数/SPC空间尺寸/SYN偏差秒数/MUS-BPM区间)
  不可修改(核心身份):
    - director_agent 的16项审计结构本身(不可增删审计维度·审计1-15+7D+16)
    - enhance 的一层WHY框架(四个决策框架不可移除)
    - 知识库§1-§10的已冻结规则(已通过10个压力测试验证)
    - 交叉升级机制的路径结构(可调触发阈值·不可删路径)
```

## 工作流程

```
EP1:
  MODE:A → Seko → MODE:F → agent修复+记录(冷启动·无历史)

EP2:
  MODE:A → Seko → MODE:F → 反馈日志累积

EP3:
  MODE:A → Seko → MODE:F → ≥3次触发→模式识别
  → 提案: 升级 enhance §3A-A5
  → 影子测试(3集回顾) → 3法官投票 → 你确认 → git commit

EP4:
  MODE:A（规则已升级）→ Seko → 观察首帧正确率变化
  → 如退化 → git revert · 如改善 → S增长
```
